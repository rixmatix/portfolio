The problem

A system everyone used and nobody followed

The design system existed. It had tokens, a component library and documentation, and most teams had adopted it. The problem was what happened after adoption. A designer would detach a component to make one change, pick a colour by eye because it was close enough, or nudge a spacing value off the grid to make something fit. Each change was small and reasonable on its own. Across [TODO: number] teams they added up to a system that looked consistent in the library and inconsistent in the product.

The only check was a design review, and a review can't scale. Reviewers caught what they happened to notice, late, after the work was done and the designer had moved on. The same mistakes were found again and again, by hand, by people whose time was better spent on the system itself.

What the reviews kept finding

  • 01

    Values instead of tokens

    Raw hex colours, hand-typed font sizes and spacing values that were close to the scale but not on it. Invisible in a file, visible in the product.

  • 02

    Detached and deprecated components

    Components detached for a one-off change and never reattached, and old versions still in use long after they'd been replaced.

  • 03

    Accessibility found last

    Contrast failures discovered in dev review or QA, after the design had been approved and built.

Approach

Make the rules executable

Every one of those findings was a rule the system already had, written down in documentation nobody re-read. If a rule can be written down, it can be checked by a machine. I set out to turn the system's rules into a linter — the same idea engineers have relied on for decades, pointed at design work.

  • principle/01

    Check early, not late

    The linter runs while the work is being made, in the designer's own file. A problem found at that point costs a click to fix. The same problem found in QA costs a sprint.

  • principle/02

    Every finding comes with a fix

    A linter that only complains gets turned off. Each rule names the nearest valid token, component or value, and applies it in one action where it safely can.

  • principle/03

    The system is the source of the rules

    Rules read the token set and component library directly. When a token is added or a component deprecated, the linter knows on the next run, with no rule rewritten.

The linter

How a pass works

Input Design file or selection
Reference Tokens + component library
Check Rules run per layer
Report Issues, grouped by rule
Fix Apply the nearest valid value

What a designer sees

The linter is a panel beside the canvas. Run it on a page or a selection and it walks every layer, compares what it finds to the token set and the library, and lists what doesn't match. Each issue names the rule, the layer, and the fix. Clicking one selects the layer; clicking the fix applies it.

Findings are grouped by rule, not by layer, because a file with forty raw colours usually has one or two mistakes repeated forty times. Fixing by rule turns forty clicks into one.

Tokens

  • Colour. Any fill, stroke or text colour that isn't bound to a token. Suggests the nearest token by colour distance; flags when nothing is close.
  • Type. Text not using a type style from the scale, or a style with a local override.
  • Spacing. Padding, gaps and offsets that aren't on the spacing scale.
  • Radius and elevation. Corner radii and shadows that aren't a system value.

Components and accessibility

  • Detached instances. Frames that were library components and no longer are, with the original named.
  • Deprecated components. Instances of anything the library has retired, with the replacement named.
  • Overrides. Instance overrides that change a property the component doesn't expose.
  • Contrast. Text-on-background pairings below WCAG AA, checked against the resolved colours.

Rollout

Warnings first, then errors

A linter that fails everything on day one gets uninstalled on day two. Every rule shipped as a warning first. Teams ran it, saw what it found, and fixed what they could. Reflection

Governance is a tool, not a meeting

The lesson I keep taking from this one is that a design system's rules are only real when something enforces them. Documentation describes the system; a linter makes it true. The second lesson is about trust: the linter only worked because every finding came with a fix and every false positive was taken seriously. Enforcement that feels like being policed gets routed around. Enforcement that feels like help gets adopted.
