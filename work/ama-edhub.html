Case study ds/edhub · AMA Ed Hub · 2026

One token system for fifty brands

AMA Ed Hub delivers accredited medical education from the AMA and more than fifty partner organizations — each with its own brand, each serving two very different audiences. I led the design of a token architecture that turned that matrix into data: one taxonomy, three accessibility modes, and a pipeline that generates every brand's theme instead of hand-building it.

Role
Design Lead, token architecture
Timeline
Jan 2026 – Apr 2026
Team
Me + partner engineering team, brand and accessibility stakeholders
Stack
Figma Variables · Style Dictionary · Claude Code · CSS custom properties

Impact

Outcomes

  • 50+partner brands running on one semantic token model
  • 300+generated themes — every brand × light, dark and high-contrast × educator and learner
  • < 1 dayto onboard a new partner brand, down from roughly three weeks of manual theming

Every text and surface pairing passes WCAG AA in light and dark, and AAA in the high-contrast set — verified by an automated audit on every build, not by a designer with a contrast checker.

The problem

A platform wearing fifty costumes

Ed Hub is one product, but partners expect their courses to feel like theirs. Each new partner arrived with a brand guide, and each one got a bespoke theme: a designer pulled colours into Figma, an engineer transcribed them into a stylesheet, and QA caught whatever fell between. Nobody owned the whole picture, because the whole picture was fifty pictures.

Underneath the brands sat a second split. Educators publish, review and track outcomes in dense, data-heavy tools; learners read, watch and take assessments in a layout built for focus. Those two audiences had drifted into two visual languages that shared a logo and little else.

What I found in the first two weeks

  • 01

    Brand as a fork

    Each partner theme was a copy of the last one with values swapped by hand. A fix to the base system had to be re-applied fifty times, so it usually wasn't.

  • 02

    Accessibility as an afterthought

    Partner colours were applied as given. Some failed AA as body text; high contrast existed only as a browser setting nobody had designed for.

  • 03

    Two products in one

    Educator and learner surfaces used different spacing, type scales and component variants, with no shared vocabulary to describe the difference.

Approach

Treat the matrix as data

Fifty brands, three modes and two audiences is three hundred themes. No team hand-builds three hundred themes, and no team should. I set three rules for the architecture before touching a single colour:

  • principle/01

    Brands change values, never names

    A partner can change what color.action.primary points at. It can't add, rename or remove a token. The vocabulary is the system; the values are the brand.

  • principle/02

    Every dimension is a layer

    Brand, mode and audience are separate layers that compose, not variants that multiply. Adding a fourth mode means one new layer, not fifty new files.

  • principle/03

    Generate, then audit

    Anything that can be derived from a brand's primitives is generated by the pipeline and checked by a script. Designers decide the rules; the build applies them.

The partner engineering team and I agreed on the contract early: the design system owns the taxonomy and the generated output; product teams consume tokens by role and never by value. That line is what let four months of work scale to fifty brands without fifty conversations.

Taxonomy

Building the stack, one layer at a time

The architecture is six layers. Each one answers a single question, and each one only knows about the layer before it. Scroll to build it.

01 / 06 · Primitives

Every raw value, no opinions

The first layer is a flat inventory: colour ramps, a type scale, a spacing grid, radii. The AMA palette lives here — and so does every partner palette, normalised into the same 50–900 ramps so every layer built on top of this one can address them identically.

02 / 06 · Semantic roles

What a value is for

Roles describe intent: text that is primary, a surface that is raised, an action that is the main one on the page. This is the vocabulary partners never see and never change. Around 140 roles cover the whole product.

03 / 06 · Component

Roles applied to parts

Component tokens alias roles, not primitives. A button's fill points at action.primary; it has no idea which blue that is. Teams theme components by changing what a role resolves to, never by editing the component.

04 / 06 · Modes

Light, dark and high contrast

Modes remap the semantic layer only. The high-contrast mode isn't a darker dark: it is a separate set tuned to pass WCAG AAA for every text pairing, with thicker hairlines and no colour-only states. It is one more column in the same table.

05 / 06 · Brands

Fifty remaps, not fifty forks

A brand is a file that says which primitives the roles use. Figma holds the AMA brand and a handful of reference partners; the other forty-plus are generated from each partner's brand guide and never need a design file.

06 / 06 · Audience

Educator and learner

The last layer carries the only differences the two audiences actually need: density, type scale and reading measure. Educators get a compact grid for tables and dashboards; learners get a comfortable one for reading. Colour never changes here.

In CSS that lands as one custom property, scoped by two attributes on the root — data-brand and data-mode — with the audience layer applied by the page template. Swapping a partner is swapping an attribute.

Pipeline

Figma holds the model; the build holds the brands

The decision that made the rest possible: Figma Variables carry the taxonomy, the AMA brand and five reference partners. The remaining partners exist only as JSON. Fifty brand modes in Figma would have been unmanageable for designers and unnecessary for engineers — partners don't get design files, they get themes.

Where the AI earned its place

I used Claude Code as a member of the team with a very specific job: the repetitive, rule-bound work that scales with the number of brands. It never decided what a role meant. It applied the rules I'd written, fifty times, and reported where they broke.

  • Brand intake. Given a partner's brand guide, it drafted the primitive ramp file: normalising their two or three brand colours into 50–900 ramps, flagging any colour that couldn't reach AA as text.
  • Transforms. It wrote and maintained the Style Dictionary config and custom transforms, including the attribute-scoped CSS output.
  • Contrast audit. Every build checks every text-on-surface pairing in every theme — AA for light and dark, AAA for high contrast — and fails the build with a readable report instead of a warning nobody reads.
  • Documentation. Each partner gets a generated theme page: their ramps, their role mappings, and a rendered component sheet.

Themes

Dark mode is a remap. High contrast is a commitment.

Light and dark were straightforward once the semantic layer existed: two columns of values for the same roles, with the primitives untouched. High contrast was the layer that tested the architecture, because AAA is not "more contrast" — it changes what the system is allowed to do.

What the AAA set changes

  • Every text pairing at 7:1 or better, including partner accents — which meant generating a darkened "text-safe" step for every brand colour rather than using the brand's own.
  • Hairlines become 2px strong borders; disabled states keep 4.5:1 instead of fading out.
  • No colour-only meaning: status chips, progress and validation gain icons and text through component tokens, so the change is automatic.
  • Focus rings resolve to a fixed high-contrast pair regardless of brand.

Because each of these is a token, the high-contrast set applies to all fifty brands the moment it exists. No partner had to be revisited.

Onboarding

A new partner is a pull request

The real test of the system was the first partner onboarded after it shipped. Their brand guide arrived on a Tuesday morning. By the afternoon they had a theme in all three modes, a contrast report, and a generated documentation page — reviewed by a designer, merged by an engineer, never opened in Figma.

The intake flow I designed with the partner team has four steps, and only the first one involves a person making a judgement call:

  1. Extract. A designer confirms the two or three brand colours and the type family from the guide.
  2. Generate. The pipeline builds the primitive ramps, a text-safe step for each accent, and the brand's role mapping from the default template.
  3. Audit. Every pairing is checked; anything failing AA or AAA is adjusted toward the nearest passing step and reported.
  4. Review. The designer reviews the rendered component sheet against the brand guide and approves or adjusts the mapping. Merge.

Three weeks to under a day is the headline number, but the quieter win is that a base-system fix now reaches all fifty partners on the next build, instead of being re-applied by hand fifty times, or not at all.

Results

From fifty themes to one system

In four months the partner team and I replaced fifty hand-maintained themes with one taxonomy of roughly 180 primitives per brand, 140 semantic roles and 210 component tokens, generating more than 300 theme outputs. Every one of them passes its accessibility target on every build.

What changed for the teams

  • Designers theme by changing role mappings in one place. Nobody copies a theme file any more.
  • Engineers consume one set of custom properties and two root attributes. Brand-specific CSS went to zero.
  • Accessibility moved from a review step to a build step. The AAA set shipped to every partner at once.
  • Educator and learner surfaces share every colour and component and differ only in the audience layer, which is now a documented, intentional difference.

Reflection

Taxonomy is the product

On a multi-brand system the colours are the least important decision. The names are the architecture: get the roles right and brands, modes and audiences become columns in a table that a machine can fill in. Get them wrong and every brand is a fork again, however good the tooling is.

Three things I'd carry to the next one:

  • Decide what Figma is for. It's the place designers reason about the model, not a database of every brand. Putting fifty modes in it would have slowed the designers and helped nobody.
  • Give the AI a rulebook, not a brief. Claude Code was most useful when the rules were explicit enough that its output could be audited mechanically. The audit script was worth more than any single generated file.
  • Design the hardest mode first. AAA forced decisions that made light and dark better too. If I'd added it last, it would have been a patch.
