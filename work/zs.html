ZS Enterprise Design System

A three-month initiative that transformed how ZS builds digital products. The existing pattern library lived in Sketch and had stopped keeping up with a fast-moving analytics business. I rebuilt it from the ground up as a token-driven, atomic design system — and onboarded two hundred designers to Figma and a new way of working.

Role
Design Lead
Timeline
Jan 2021 – Apr 2021
Team
Me + two engineering leads
Stack
Sketch → Figma · design tokens · atomic design

Impact

Outcomes

  • 72new dynamic components documented and published
  • 200+designers trained and onboarded to the new system

The project addressed fundamental challenges around consistency, quality and accessibility across ZS's enterprise analytics platform — and replaced a static library with one a team of two hundred could actually build on.

The problem

A fast-moving analytics business, a static library

ZS's design team was working in a fragmented design ecosystem. The existing pattern library lived in Sketch, which created real barriers to collaboration and efficiency: components were static, hard to share, and drifted the moment they were copied into a working file. For a design team of 200 working alongside 1,200 engineers, the library had become a bottleneck rather than a foundation.

Observations

  • finding/01

    Broken components, many tools

    Components were scattered across multiple tools, and many were broken or out of date. There was no reliable place to go for the current version of anything.

  • finding/02

    Static, inflexible assets

    Design assets couldn't adapt to evolving needs. Changing content or state meant detaching and redrawing, so every instance became a one-off.

  • finding/03

    No single source of truth

    Without one, products diverged. The same control looked and behaved differently from one product to the next, and nobody could say which was right.

  • finding/04

    Scale the library couldn't meet

    Two hundred designers and twelve hundred engineers need a system that scales with them. A Sketch library maintained by hand does not.

Approach

Rebuild, don't convert

Rather than simply converting the existing Sketch files, I architected a new system from the ground up using industry best practices. Converting would have carried every foundational problem into Figma. Starting fresh let us fix them.

  • 01

    Atomic design

    Followed the atomic methodology to create a logical, scalable component hierarchy — atoms, molecules and organisms that compose instead of duplicate.

  • 02

    Token architecture

    Installed tokens for consistent design decisions across every component, so a change to a colour, type or spacing value lands everywhere at once.

  • 03

    Documentation

    Comprehensive documentation to support adoption across a large, distributed team. A component nobody knows how to use isn't a component.

Process

Four phases in three months

Phase 1 Audit & strategy
Phase 2 Token foundation
Phase 3 Component build
Phase 4 Documentation

Audit & strategy

Analyzed the existing patterns and identified the gaps before designing anything new.

  • Gathered end-to-end experiences across the platform
  • Looked at usage patterns: which components were used, where, and how often
  • Interviewed designers on their pain points
  • Analyzed the existing files and components

Token foundation

Established the design tokens — colour, typography, spacing and more — that every component would be built on.

  • Designed a token architecture that could accommodate brand flexibility
  • Ensured WCAG AA compliance across the colour system
  • Spread the token structure into the components, so no value lives in a component by hand

Component build

Systematically rebuilt 70+ components using atomic design principles, and kept the whole design org in the loop while it happened.

  • Rebuilt components for dynamic content and flexibility, so they adapt instead of being detached
  • Two Slack channels: one for announcements, one for async collaboration
  • Weekly updates sharing progress, upcoming work and adoption metrics

Documentation

Created clear guidance for proper component usage, written for a designer who has never seen the system before.

  • Documentation for each component's usage and the triggers that call for it
  • Covered the whole component user experience, not just the visual spec

Release

An org-wide onboarding, then a month of momentum

At the start of the project we promised an org-wide onboarding session for the new system, and after three months of work we delivered it. Not every designer could attend, and adoption still reached 25% in the first week. With continued training and onboarding it grew to 75% after a month.

Phased adoption with training support beat expecting everyone to switch at once. The Slack channels and weekly updates from the build phase became the support system for the rollout.

Results

What changed for the teams

The new ZS Design Library transformed how the design and engineering teams work together:

  • 25% adoption in the first week after the onboarding session.
  • 75% adoption after a month, with continued training and onboarding.
  • 20% reduction in the time it takes to create new experiences and applications.
  • 200 designers successfully onboarded from Sketch to Figma and a completely new workflow.

Key learnings

What leading the migration reinforced

  • learning/01

    Documentation is as important as components

    Great components mean nothing if people don't know how to use them.

  • learning/02

    Phased adoption beats a hard cutover

    Phased adoption with training support drives higher success rates than expecting immediate, full adoption.

  • learning/03

    Tokens upfront save hours later

    Putting the token architecture in place first saved countless hours of updates down the line.

  • learning/04

    Rebuilding > converting

    Starting fresh allowed us to fix foundational issues rather than perpetuating them.
